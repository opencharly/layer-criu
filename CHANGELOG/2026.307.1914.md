**The pre-flight.** `criu check --unprivileged --feature seccomp_suspend`, run from the namespace the rootful daemon runs in, requiring **both** a zero exit status and the line `seccomp_suspend is supported`. The named `--feature` form short-circuits CRIU's own check, so the exit status IS the feature result; the bulk `--extra` form is never a gate because it is non-zero even on a host that checkpoints perfectly (`UFFD is not supported`). The two gates report on **different streams** — the capability gate on stdout, the seccomp probe on stderr — so each is captured to its own file and the success line is required in either.

## How tested

**The required bed, on the committed tree `dc81ce9`:**

```console
$ charly check run check-criu-vm
PASS (steps=11)      rc=0
plan: 3 steps: 3 passed, 0 failed, 0 skipped

  PASS  criu-absent-before-install          exit=0
  PASS  criu-installed-on-guest             exit=0
  PASS  criu-seccomp-suspend-on-guest       exit=0
```

The bed is the **three-step shape** the check skill prescribes, all on a disposable guest:

1. **ABSENT** — `criu` is removed from the guest and `command -v` must be empty. *(It removes rather than asserts absence because the Fedora 43 cloud base SHIPS criu — measured; a "fresh guest has none" arm was false. Removing an absent package is a no-op, so the step is idempotent.)*
2. **PERFORM** — `dnf install -y criu`, then `test -x /usr/bin/criu && /usr/bin/criu --version`.
3. **PRESENT** — the pre-flight returns **0** AND prints `seccomp_suspend is supported`, read from both streams, **on the guest's own kernel**. This is the assertion A2 said had never executed: in box mode it skips with `context [runtime] not active in box mode`, and no disposable target existed.

The steps run at `deploy-add` **and** at `check-live`, so the fresh-rebuild pass re-evaluates them against the rebuilt guest rather than passing by coincidence.

**What building the bed found, both now in the file's own comments:**

- **`in_container: false` runs on the machine running charly, not the guest.** Measured with diagnostics inside the guest probe: `in_container: false` → `id=atrawog`, no `/usr/bin/criu`, `sudo -n true` rc=0; `in_container: true` and the field **absent** both reached the guest and the probe passed. The candy therefore keeps `in_container: false` — right for its consumers (a pod venue's "in container" is not the daemon's namespace; a host deploy's venue IS the host) — and the bed asserts the same **contract** on the guest instead of composing a host-targeted plan and expecting it green.
- **`as_root criu …` resolved the binary through sudo's PATH** and produced `sudo: criu: command not found`, then reported it as *"this host cannot suspend the target's seccomp filter"* — a false negative on the one gate the dump path depends on. Both the candy's and the bed's probes now use the absolute `/usr/bin/criu` the check already asserts exists.

**R7 — emitted artifacts.** This repo builds **no image**: it declares a `candy:` layer and a `vm:` bed, so there is no Containerfile and no `ai.opencharly.*` label emitted here to inspect. The candy's labels are emitted when a **consumer** composes it (`layer-containerd`'s host box, `pod-crabbox`'s image), and that assertion belongs to the consumer's build, not to this repo. Stated explicitly because the prior verdict raised it twice and the honest answer is "not applicable, and here is why", not silence.

**Not run, stated rather than implied:** the pre-flight has not been executed against a host with a **running** rootful containerd daemon — the bed proves the kernel/namespace capability on a disposable guest, which is what the check asserts, but the daemon-namespace case needs a bed that installs the host layer too.
